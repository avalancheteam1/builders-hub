**By the end of this lesson you will be able to:**

- Generate a Solidity verifier and deploy it to Fuji
- Recognise the two silent failure modes that make a valid proof return false
- Break down verification gas by component

In this lesson we'll take everything from Module 3 on-chain. The circuit you compiled becomes a Solidity contract, that contract goes to Fuji, and a proof generated in your terminal gets checked by the EVM.

This is the same pipeline eERC's production contracts run. The circuits are larger and the surrounding logic is more careful, but the stages are identical.

We'll use the hash preimage circuit from the previous module as the running example, so if you followed along there you already have the first three artifacts.

<Steps>
<Step>

**Compile and set up.**

Recapping the commands from Module 3, since you need their outputs here:

```bash
circom circuit.circom --r1cs --wasm --sym -l node_modules -o build

npx snarkjs groth16 setup build/circuit.r1cs powersOfTau28_hez_final_12.ptau circuit_0000.zkey
npx snarkjs zkey contribute circuit_0000.zkey circuit_final.zkey \
  --name="first contribution" -e="some random text"
```

Before going further, check what you built:

```bash
npx snarkjs r1cs info build/circuit.r1cs
```

The constraint count determines your proving key size and which Powers of Tau you needed, but it has **no effect** on the gas cost of what you're about to deploy. That decoupling is why Groth16 is used for on-chain verification in the first place.

</Step>
<Step>

**Export the Solidity verifier.**

```bash
npx snarkjs zkey export solidityverifier circuit_final.zkey Verifier.sol
```

The generated contract is self-contained: verification key baked in as constants, pairing check implemented against the precompiles, no dependencies. Its interface looks like this:

```solidity
function verifyProof(
    uint[2] calldata _pA,
    uint[2][2] calldata _pB,
    uint[2] calldata _pC,
    uint[1] calldata _pubSignals
) public view returns (bool)
```

- `_pA` and `_pC` are the G1 points of the proof
- `_pB` is the G2 point, represented as a 2×2 array because G2 coordinates live in a quadratic field extension
- `_pubSignals` is sized to your circuit's public inputs, here just the hash

Internally it validates that the points are on the curve, computes the linear combination of public inputs against the verification key, calls `ecPairing` at `0x08` with four pairs, and returns the result.

<Callout type="info">
The generated contract's name is `Groth16Verifier`, not the filename. If your deploy script cannot find the artifact, that is usually why.
</Callout>

</Step>
<Step>

**Deploy to Fuji.**

<Callout type="warn">
Install Hardhat 2 explicitly: `npm install --save-dev hardhat@^2.22.0 @nomicfoundation/hardhat-toolbox@^5`. A bare `npm install hardhat` now pulls Hardhat 3, which expects an ESM or TypeScript config and will not load the CommonJS `hardhat.config.js` below.
</Callout>

```javascript
// hardhat.config.js  (Hardhat 2)
require("@nomicfoundation/hardhat-toolbox");

module.exports = {
  solidity: "0.8.20",
  networks: {
    fuji: {
      url: "https://api.avax-test.network/ext/bc/C/rpc",
      chainId: 43113,
      accounts: [process.env.PRIVATE_KEY]
    },
    avalanche: {
      url: "https://api.avax.network/ext/bc/C/rpc",
      chainId: 43114,
      accounts: [process.env.PRIVATE_KEY]
    }
  }
};
```

```javascript
// scripts/deploy.js
const hre = require("hardhat");

async function main() {
  const Verifier = await hre.ethers.getContractFactory("Groth16Verifier");
  const verifier = await Verifier.deploy();
  await verifier.waitForDeployment();
  console.log("Verifier deployed to:", await verifier.getAddress());
}

main().catch((e) => { console.error(e); process.exit(1); });
```

```bash
npx hardhat run scripts/deploy.js --network fuji
```

Nothing here is Avalanche-specific beyond the RPC URL and chain ID. Get test AVAX from the [Fuji faucet](https://core.app/tools/testnet-faucet/) if you need it.

</Step>
<Step>

**Generate a proof and submit it.**

```bash
node build/circuit_js/generate_witness.js \
  build/circuit_js/circuit.wasm input.json witness.wtns
npx snarkjs groth16 prove circuit_final.zkey witness.wtns proof.json public.json
```

```javascript
const { ethers } = require("hardhat");
const proof = require("./proof.json");
const publicSignals = require("./public.json");

async function verify() {
  const verifier = await ethers.getContractAt(
    "Groth16Verifier",
    process.env.VERIFIER_ADDRESS
  );

  const result = await verifier.verifyProof(
    [proof.pi_a[0], proof.pi_a[1]],
    [
      [proof.pi_b[0][1], proof.pi_b[0][0]],   // note the swap
      [proof.pi_b[1][1], proof.pi_b[1][0]]
    ],
    [proof.pi_c[0], proof.pi_c[1]],
    publicSignals
  );

  console.log("Proof valid:", result);
}

verify();
```

<Callout type="warn">
The inner arrays of `pi_b` are reversed relative to what the Solidity verifier expects. snarkjs serializes G2 coordinates in one order and the generated contract reads them in the other.

Get this wrong and `verifyProof` returns `false` for a perfectly valid proof, with no error and nothing to debug. It's comfortably the most common reason a first deployment appears broken. If you'd rather not hand-write the ordering, `npx snarkjs zkey export soliditycalldata public.json proof.json` prints the arguments correctly formatted.
</Callout>

</Step>
<Step>

**Break it on purpose.**

Reading about a silent failure is not the same as recognising one at 2am. Trigger both failure modes now, while you know the proof is good.

First, remove the coordinate swap — change the `pi_b` block to the order snarkjs gave you:

```javascript
[
  [proof.pi_b[0][0], proof.pi_b[0][1]],   // swap removed
  [proof.pi_b[1][0], proof.pi_b[1][1]]
],
```

Run it again. You should see `Proof valid: false`. No revert, no error message, no gas anomaly — the transaction succeeds and simply reports failure. That is what a G2 ordering bug looks like from the outside.

Now restore the swap and instead change one public signal:

```javascript
publicSignals[0] = "1";   // a hash you never proved
```

`false` again, and for a completely different reason: the proof is valid, but not for the statement you just asked about.

Both bugs produce byte-identical symptoms. This is why the debugging advice is to check the calldata encoding *before* suspecting the circuit — the verifier cannot tell you which of the two happened, and it never will.

</Step>
</Steps>

### The precompiles it depends on

| Address | Operation | Gas |
|---|---|---|
| `0x06` | `ecAdd` on BN254 G1 | 150 |
| `0x07` | `ecMul` on BN254 G1 | 6,000 |
| `0x08` | `ecPairing` | 45,000 + 34,000 per pair |

These run native code inside AvalancheGo instead of EVM bytecode, which is where the efficiency comes from. C-Chain and Fuji implement them identically to Ethereum mainnet, so a verifier written for one deploys unchanged to the others.

## Wiring It Into an Application

In production, users don't call the verifier directly. An application contract does, as a gate on its own logic:

```solidity
// SPDX-License-Identifier: MIT
pragma solidity ^0.8.20;

interface IVerifier {
    function verifyProof(
        uint[2] calldata _pA,
        uint[2][2] calldata _pB,
        uint[2] calldata _pC,
        uint[1] calldata _pubSignals
    ) external view returns (bool);
}

contract PrivateAction {
    IVerifier public immutable verifier;
    mapping(uint256 => bool) public usedHashes;

    event ActionExecuted(address indexed caller, uint256 indexed hash);

    constructor(address _verifier) {
        verifier = IVerifier(_verifier);
    }

    function executeWithProof(
        uint[2] calldata a,
        uint[2][2] calldata b,
        uint[2] calldata c,
        uint[1] calldata pubSignals
    ) external {
        require(verifier.verifyProof(a, b, c, pubSignals), "invalid proof");

        uint256 hash = pubSignals[0];
        require(!usedHashes[hash], "already used");
        usedHashes[hash] = true;

        emit ActionExecuted(msg.sender, hash);
        // application logic here
    }
}
```

The ordering here isn't stylistic. Verify, then check replay, then write state, then act.

A revert does undo every state change and every log in the frame, so ordering isn't about salvaging a failed transaction. It matters for two other reasons. Once an external call follows a write, anything you wrote before verifying is state an attacker can reenter against. And work done ahead of the verification is gas the caller pays for even when the proof turns out to be invalid.

<Callout type="warn">
The `usedHashes` check above is doing real work. Without it, anyone who observes a successful transaction can resubmit the identical proof, because a Groth16 proof carries no notion of who submitted it or when. The next lesson covers binding proofs to a sender, which is the stronger version of this.
</Callout>

## What It Costs

The verifier we just deployed has **one** public signal, so it performs one `ecMul` and one `ecAdd` to fold that signal into the verification key, then a single pairing check over four pairs. The precompile prices come from [EIP-1108](https://eips.ethereum.org/EIPS/eip-1108): 6,000 for `ecMul`, 150 for `ecAdd`, and 45,000 + 34,000 per pair for `ecPairing`.

| Component | Gas |
|---|---|
| Calldata, proof plus public inputs | ~4,100 |
| `ecMul`, 1 public signal | 6,000 |
| `ecAdd`, 1 public signal | 150 |
| `ecPairing`, 4 pairs | 181,000 |
| Solidity overhead | ~5,000 |
| **Verification total** | **~196,000** |

This is lower than the ~230,000 the course quotes elsewhere, and the difference is entirely the public-input count. Module 2's table put a single-signal verifier at ~196,000 and an eight-signal one at ~239,000; ~230,000 is the typical application circuit, while the one you just deployed is the cheapest case. The pairing check is identical in both — only the per-signal row moved.

The C-Chain minimum base fee is **1 wei**, set by [ACP-176](/docs/acps/176-dynamic-evm-gas-limit-and-price-discovery-updates) in the Fortuna upgrade of April 2025. (You may still see older material quoting 1 nAVAX; that was [ACP-125](/docs/acps/125-basefee-reduction), shipped with Etna in December 2024 and superseded since.) The floor is not what you actually pay — the base fee rises with demand — but under normal C-Chain load it sits well below 1 nAVAX, which puts a verification in the region of a small fraction of a cent.

Adding application logic on top, such as balance updates, events, and storage writes, typically brings a full private transaction to 300,000 to 400,000 gas.

Keep that number in mind.
